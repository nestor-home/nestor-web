This is the standard every satellite implements, version 1 ([changelog](#13-changelog)). The core’s
black-box [conformance suite](/docs/satellites/conformance/) checks SDKs and drivers against it.

A **satellite** is a device paired with a Nestor server (the **core**). It talks with the assistant
in writing, aloud or both, reports observations and carries out the core’s intents.

MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are read as in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). The core’s message classes
(`nestor.modules.satellites.wire`) define each message; their JSON Schemas are served at
`https://nestorhome.dev/schemas/satellite/1/<message>.json` ([Schemas](/docs/satellites/schemas/)).

## 1. Overview

A satellite goes through three phases, in this order:

1. **Pairing**, once: a person proves they meant to pair the device
   ([section 2](#2-pairing-methods)), and the core hands it a token ([section 3](#3-pairing)).
2. **The link**, while the device runs: a WebSocket opened with the token, carrying every message
   ([section 7](#7-link)).
3. **Audio**, only for a device allowed it: a WebRTC connection tied to the link, carrying audio
   only ([section 9](#9-audio)).

## 2. Pairing methods

The device declares the methods it supports and the person picks one. A **device code** goes from
the device to the person, who types it in the admin. An **enrollment code** goes from the admin to
the device, which presents it to the core.

| Method                    | Proof           | The person…                                                                          |
| ------------------------- | --------------- | ------------------------------------------------------------------------------------ |
| `device_code.display`     | device code     | reads the code on the device’s screen and types it in the admin                      |
| `device_code.speech`      | device code     | hears the device say its code and types it in the admin                              |
| `enrollment.input`        | enrollment code | types the enrollment code on the device                                              |
| `enrollment.provisioning` | enrollment code | sets the pairing URI or code in the device’s configuration (flag, environment, file) |
| `enrollment.qr`           | enrollment code | shows the pairing URI’s QR code to the device’s camera                               |

Identify ([section 6](#6-identify)) is a capability, not a method.

### 2.1 Negotiation

- **N1.** A manifest MUST list the methods the device supports in `pairing_methods`, at least one,
  without repetition. A device MUST NOT declare a method it cannot carry out.
- **N2.** The core recommends the first method the device supports in this order:
  `device_code.display`, `device_code.speech`, `enrollment.qr`, `enrollment.input`,
  `enrollment.provisioning`. For a device that has not contacted the core yet, every method is
  offered. The admin highlights the recommended one and keeps the others available.
- **N3.** The device never imposes a method. Whatever the person picks, the device MUST accept both
  proofs until one is accepted (section 3.3).

## 3. Pairing

### 3.1 Endpoints

All bodies are JSON (`Content-Type: application/json`).

| Request                                             | Body                 | Answer                 |
| --------------------------------------------------- | -------------------- | ---------------------- |
| `POST /satellites/pairings`                         | `pairing.request`    | `201` `pairing.ticket` |
| `POST /satellites/pairings/{pairing_id}/enrollment` | `pairing.enrollment` | `200` `pairing.state`  |
| `GET /satellites/pairings/{pairing_id}`             |                      | `200` `pairing.state`  |

```json
POST /satellites/pairings
{"manifest": {"protocol": "nestor.satellite/1",
              "device": {"id": "capteur-entree", "model": "esp32", "room": "entree"},
              "software": {"name": "nestor-satellite", "version": "0.5.0"},
              "capabilities": [{"name": "device.identify"}],
              "pairing_methods": ["enrollment.provisioning", "enrollment.qr"]},
 "enrollment_code": "K7QF2M9X", "method": "enrollment.provisioning"}

201 {"pairing_id": "…", "status": "approved", "expires_at": "2026-10-30T12:10:00+00:00"}
201 {"pairing_id": "…", "status": "pending", "expires_at": "…", "device_code": "042917"}   (without a code)

GET /satellites/pairings/{pairing_id}
200 {"status": "pending", "identify": true}
200 {"status": "approved", "token": "nst1_…", "device_id": "capteur-entree", "room": "entree",
     "capabilities": ["device.identify"]}
```

Errors answer `pairing.error`: `{"error": code, "detail": text, "reason"?: …, "retry_after_s"?: …}`.

| `error`                | Status | Meaning                                                                                    |
| ---------------------- | ------ | ------------------------------------------------------------------------------------------ |
| `invalid_request`      | 422    | the body does not follow its schema                                                        |
| `protocol_unsupported` | 422    | the manifest names another version of this protocol                                        |
| `too_many_pending`     | 429    | too many devices wait for a proof; `Retry-After` and `retry_after_s` say when to try again |
| `too_many_attempts`    | 429    | too many wrong enrollment codes; `Retry-After` and `retry_after_s` say when to try again   |
| `enrollment_refused`   | 403    | the enrollment code pairs nothing; `reason` is `unknown`, `expired`, `used` or `cancelled` |
| `not_pending`          | 409    | the pairing no longer waits for a proof: the other proof won, or it expired                |

`detail` is English, for logs. A device that shows or says an error MUST translate it from `error`
and `reason`, never show `detail`.

### 3.2 States of a pairing

<PairingStates locale="en" n={2} />

- A pending pairing lasts 10 minutes. An unknown, superseded or forgotten `pairing_id` reads as
  `expired`, so polling reveals nothing.
- Only the first `approved` answer carries the token; later polls read `claimed`.

### 3.3 Device rules

- **P1.** A device MUST support `enrollment.provisioning`: it reads a pairing URI from
  `NESTOR_PAIRING_URI`, or an enrollment code from `NESTOR_PAIRING_CODE` with the core’s address
  given separately. It SHOULD also accept both from a command-line flag and its configuration file.
- **P2.** With no enrollment code, a device MUST request a pairing and present its device code on
  every output it has: on a screen (`device_code.display`), aloud, and always in its log. Aloud
  (`device_code.speech`) is a short sentence, then the digits one by one with a pause between them,
  the whole said twice, in the device’s language, without the network. A device with neither
  screen nor voice MUST log the device code and that an enrollment code pairs it. The device polls
  about once a second until the pairing is approved or expires, and requests again on expiry.
- **P3.** A device with an enrollment code MUST send it in its request, with the method it received
  it by. It MUST NOT present a device code unless that code is refused.
- **P4.** A pending device MUST accept an enrollment code at any time (typed, scanned, configured) and
  send it to `POST …/{pairing_id}/enrollment`. The first proof accepted wins:
  - if the device code was typed first, the enrollment answers `not_pending` and the enrollment code
    is **not** spent: the device keeps polling and gets its token;
  - if the enrollment code was accepted first, the device code typed afterwards is refused.
    On `approved`, the device stops presenting its device code at once (a voice falls silent).
- **P5.** An enrollment code refused with `enrollment_refused` MUST NOT be presented again, even after
  a restart: the device keeps the refused codes with its token (a hash of each is enough). It MUST
  say so in its log (and on its outputs, translated), then fall back to a device code (P2).
- **P6.** On `429`, a device MUST wait at least `Retry-After` seconds before trying again.
- **P7.** Enrollment codes MUST be normalised before they are sent (section 4.2). A device MAY send
  them as typed: the core normalises too.
- **P8.** A device MUST keep its token secret (readable by its owner only on a file system), forget
  it when the core refuses it (link closed with `4401`, or `401` on an audio offer), then pair again.

### 3.4 Core rules

- **C1.** The core accepts the protocol versions it speaks, today only `nestor.satellite/1`. A
  manifest naming another `nestor.satellite/<n>` is refused with `protocol_unsupported`. A later core
  may also accept the version just before its own, so that devices can be updated after it.
- **C2.** An enrollment code pairs one device. It is spent as soon as it is accepted, before anything
  else can observe it: of two devices racing with it, one is approved and one gets
  `enrollment_refused` (`used`).
- **C3.** A proof is accepted only while its pairing is `pending`; the first one accepted moves it to
  `approved` at once. An enrollment code refused because the pairing is no longer pending is not
  spent.
- **C4.** The token is 256 random bits, prefixed `nst1_`; only its SHA-256 is kept.
- **C5.** Asking again with the same device id replaces the earlier pending request.
- **C6.** The journal records every step: `satellite.pairing.requested` (with the declared methods),
  `satellite.addition.started|completed|cancelled|expired`, `satellite.enrollment.refused` (with its
  reason and address), `satellite.paired` (with the proof, the method and the addition),
  `satellite.identify.requested`, `satellite.revoked`, then `satellite.connected` (with the software
  and protocol of each `hello`) and the updates (section 10). Never a code or a token in clear.

### 3.5 Additions

An **addition** is how a person adds a satellite from the admin: a method, and optionally a name, a
room and the most capabilities to allow. It lasts 15 minutes by default (1 minute to 7 days).

- With an enrollment method, the addition makes the enrollment code, returned once with its pairing
  URI. The device that presents it is paired at once, with the addition’s name and room, its
  declared capabilities narrowed to the addition’s.
- With a device code method, the admin lists the pending devices. The person tells them apart
  (identify) and types the right one’s code; the addition’s name, room and capabilities apply.

An addition ends when its device is paired (`completed`), is cancelled, or expires. At most 32 run at
once. The core claims an addition in one step: if two people type codes for it at the same instant,
one device pairs and the other person is told the addition is over.

## 4. Codes and URI

### 4.1 Device code

Six random decimal digits (`042917`), unique among pending pairings.

### 4.2 Enrollment code

- Eight symbols of Crockford’s base32 alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`: 40 random bits.
- Shown grouped by four: `K7QF-2M9X`.
- Normalisation, before any comparison: remove spaces and dashes, upper-case, then map `O` → `0`,
  `I` and `L` → `1`. A result that is not 8 symbols of the alphabet is no code (`U` is never one).
- Canonical form: the normalised 8 symbols, without the dash.

### 4.3 Pairing URI

```text
nestor+http://nestor.local:8471/?code=K7QF2M9X
nestor+https://nestor.example.org/satellites-proxy/?code=K7QF2M9X
```

- The scheme is `nestor+` followed by the scheme of the core’s base URL (`http` or `https`). Removing
  `nestor+` and the query gives the base URL.
- `code` is the enrollment code, canonical form.
- The admin returns the URI; a front renders its QR code itself.

## 5. Manifest

```json
{
  "protocol": "nestor.satellite/1",
  "device": { "id": "salon", "model": "reachy-mini", "room": "salon", "brand": "pollen-robotics" },
  "software": { "name": "nestor-reachy", "version": "0.4.0" },
  "capabilities": [{ "name": "audio.capture" }, { "name": "audio.playback" }, { "name": "device.identify" }],
  "pairing_methods": ["device_code.speech", "enrollment.provisioning"]
}
```

`id` and `room` are lowercase slugs (`^[a-z0-9][a-z0-9_-]{0,63}$`). Capabilities are `family.feature`
names, at most 32, each declared once. The manifest is sent when pairing and in `hello`.

`software` is required: the package the device runs, named as it is installed (`nestor-reachy` from
PyPI, `@nestor-home/satellite` from npm), and its version, each 1 to 64 characters. The admin shows
it, and a device that updates itself (section 10) installs newer versions of this package.

| Capability                | The device…                                    |
| ------------------------- | ---------------------------------------------- |
| `text.input`              | sends what a person typed (section 8)          |
| `text.display`            | shows the assistant’s words (section 8)        |
| `audio.capture`           | sends its microphone (section 9)               |
| `audio.playback`          | plays the core’s voice (section 9)             |
| `audio.speech_activity`   | reports when someone starts and stops speaking |
| `vision.person_detection` | reports the people it sees                     |
| `expression.emotion`      | shows the assistant’s emotions                 |
| `motion.head`             | moves with the assistant’s speech              |
| `device.identify`         | makes itself noticed on request (section 6)    |
| `device.update`           | installs a newer version of its software on request (section 10) |

A device with neither `text.*` nor `audio.*` is a sensor or a body: it only reports observations and
carries out intents.

## 6. Identify

- **I1.** A device declaring `device.identify` MUST, on a pending poll answer carrying
  `"identify": true`, make itself noticed for a few seconds with the outputs it has (blink, wiggle,
  chime, flash its screen), and keep polling.
- **I2.** Once paired and allowed `device.identify`, it MUST acknowledge `intent.identify` like any
  intent, and make itself noticed the same way.
- **I3.** The core sends identify only to a device that declared it (pending) or was allowed it
  (paired). The admin refuses it otherwise, and for a paired device that is not connected.
- Identify only helps a person tell devices apart. It proves nothing and never replaces a code.

## 7. Link

- **L1.** With its token, the device opens a WebSocket on `/satellites/{device_id}/link`, under the
  core’s base URL (`ws://` for `http`, `wss://` for `https`). Its first message MUST be `hello`: its
  manifest, with the paired device id, and its token. The core answers `welcome`: the paired room
  and the capabilities allowed.
- **L2.** The core closes the link without a `welcome` when `hello` is late (10 s), off-contract or
  for another device (`4400`), or when the token is refused (`4401`). On `4401` the device MUST
  forget its token and pair again (P8).
- **L3.** Every message is `{"type", "id", "at", "payload"}`, one per WebSocket text frame. The device
  MUST acknowledge each `intent.*` with `ack` within a second, and MUST only send what it was
  allowed: observations, `input.text` (section 8), `update.status` (section 10). Unknown message types from the core are ignored.
- **L4.** A device holds one link. A new link of the same device replaces the earlier one, which the
  core closes with `4409`. The core pings every 20 s (WebSocket pings). A device that sees them
  SHOULD treat 60 s without any as a lost link; one that cannot (a browser’s WebSocket hides them)
  relies on the transport closing the link.
- **L5.** After the core closes the link (`1001` when it stops) or the link is lost, the device
  reconnects with the same token, waiting longer between attempts.

| Close code | Meaning                                          | The device…                      |
| ---------- | ------------------------------------------------ | -------------------------------- |
| `1001`     | the core is stopping                             | reconnects (L5)                  |
| `4400`     | `hello` late, off-contract or for another device | fixes itself, then reconnects    |
| `4401`     | the token is refused                             | forgets it and pairs again (P8)  |
| `4409`     | a newer link of this device replaced this one    | stops: the other link is current |

## 8. Text

- **T1.** A device allowed `text.input` sends what a person typed as `input.text`. Each one is a turn
  in the conversation of the device’s room.
- **T2.** A device allowed `text.display` receives the assistant’s words as `intent.text`, in order,
  and shows them. An answer may take several messages (a progress note, then the result); `final`
  marks the last one of a turn. An unprompted message (a reminder, an announcement) is one
  `intent.text` with `final` set.
- **T3.** A typed turn is answered in writing when the device was allowed `text.display`, otherwise
  aloud. A spoken turn is answered aloud; a device also allowed `text.display` shows the same words
  as they are said.
- **T4.** `input.text` holds 1 to 4,000 characters, `intent.text` up to 16,000. Text is plain, without
  Markdown.

## 9. Audio

- **A1.** A device allowed `audio.capture` or `audio.playback` (in `welcome`) offers WebRTC once
  welcomed: `POST /satellites/{device_id}/audio` with `Authorization: Bearer <token>` and
  `{"sdp", "type"}`; the core answers `{"sdp", "type", "pc_id"}`. ICE candidates follow with `PATCH`
  on the same path. A wrong token gets `401`; a device without a link or not allowed audio, `403`;
  another device’s `pc_id`, `403`.
- **A2.** The connection carries Opus audio only: the core’s voice to the device (`audio.playback`),
  the microphone to the core (`audio.capture`). Messages never go through WebRTC.
- **A3.** The audio lives with the link: when the link closes, the core hangs up the audio. While the
  link is up, a device whose audio fails offers again, waiting longer between attempts.
- **A4.** A device opens its microphone only for this connection. Pairing and the link never wait for
  it, since a browser may be waiting for a person to allow the microphone.

## 10. Updates

A device allowed `device.update` installs a newer version of its own software when a person asks
for it in the admin. The core never names a source or a file: it only passes on the version the
device found itself. A compromised core can at most ask a device for a version it already trusts.

```json
{"type": "update.status", "id": "…", "at": "…", "payload": {"state": "available", "version": "0.5.1", "notes": "https://github.com/…/releases/tag/v0.5.1"}}
{"type": "intent.update", "id": "…", "at": "…", "payload": {"version": "0.5.1"}}
```

| `state`      | Means                                                                        | `version`    |
| ------------ | ---------------------------------------------------------------------------- | ------------ |
| `current`    | it found nothing newer                                                       | absent       |
| `available`  | a newer version can be installed                                             | that version |
| `installing` | it installs that version, then starts again on it                            | that version |
| `failed`     | the version did not install or did not start: it went back to the one it ran | that version |

- **U1.** A device declares `device.update` only if it can install its software itself. Once
  welcomed and allowed it, the device looks for a newer version of `software.name` at its own source
  (the index it was installed from, never an address given by the core), and reports `update.status`
  at the start of each link. It looks again at most once a day.
- **U2.** It acknowledges `intent.update` like any intent, and installs only the newer version it
  found and reported. An older version, or one it never reported, is acknowledged and not installed.
- **U3.** It reports `installing`, installs the version, then starts again on it. The new version
  MUST be welcomed within 60 s; otherwise the device goes back to the version it ran and reports
  `failed` with the version it tried. An install that fails reports `failed` too.
- **U4.** The core sends `intent.update` only when a person asks in the admin, only to a connected
  device allowed `device.update`, and only with the version that device reported as `available`.
  The journal records `satellite.update.requested` and each state the device reports
  (`satellite.update.reported`); the new version shows in the next `satellite.connected`.
- **U5.** With any state but `current`, a device MAY add `notes`: an https address (at most 512
  characters) of what that version changes, found at the same source. The admin shows it as a link
  the person's browser opens; the core never fetches it.

## 11. Security considerations

- **Entropy.** An enrollment code has 40 bits. With at most 32 codes in progress and 5 wrong codes
  per minute and address (20 from all addresses), the 300 guesses of a 15-minute lifetime hit a
  code about once in 10⁸. A device code has 20 bits, but only a signed-in person types it, on a
  pending pairing they picked, within 10 minutes.
- **Lifetime.** Enrollment codes last 15 minutes by default, 7 days at most; device codes 10 minutes.
  An accepted enrollment code is spent at once (C2).
- **Rate limits.** Wrong enrollment codes are counted per client address and overall, over a sliding
  minute. Past either limit, every attempt, right or wrong, gets `429` until the window frees a
  slot: a limited client learns nothing.
- **Hashing.** Only SHA-256 hashes of codes and tokens are stored and journaled, and compared in
  constant time. A leaked hash of a 40-bit code can be brute-forced offline: keep lifetimes short.
- **Transport.** Codes and tokens cross the network in clear over `http` and `ws`; use `https` (a
  `nestor+https` URI, hence `wss`) outside a trusted home network. The core never logs `hello`’s
  token.
- **Identify** shows which device answers, not that it is the one the person holds: never pair on
  identify alone.
- **Consent.** A device gets only the capabilities a person allowed, never more than it declared.
- **Updates.** A device fetches a new version from its own source, with that source’s integrity
  checks, and only the version it reported (U1, U2). A device that cannot update itself safely
  declares no `device.update`.

## 12. Conformance

The [conformance suite](/docs/satellites/conformance/) checks the device rules:

| Check                                                                                      | Rules  |
| ------------------------------------------------------------------------------------------ | ------ |
| declares enrollment.provisioning                                                           | N1, P1 |
| asks to pair; claims its token once its device code is typed                               | P2     |
| keeps polling after a pending identify (when it declares `device.identify`)                | I1     |
| opens its link with its token; sends a hello first; introduces itself as the paired device | L1     |
| acknowledges each intent within 1 s (`intent.identify`, `intent.update` when allowed)      | L3, I2 |
| reports where its software stands (when it declares `device.update`)                       | U1     |
| never installs a version it did not report (when it declares `device.update`)              | U2     |
| every message follows the schema                                                           | L3     |
| forgets a refused token and pairs again                                                    | L2, P8 |
| reconnects with the same token after the core closes the link                              | L5     |
| acknowledges `intent.text` (when it declares `text.display`)                               | L3, T2 |
| receives the core’s audio; sends its microphone audio (when it declares `audio.*`)         | A1, A2 |
| offers no audio when audio is not allowed                                                  | A1     |
| pairs with the enrollment code of `NESTOR_PAIRING_URI`, no code typed                      | P1, P3 |
| falls back to a device code after its enrollment code is refused (wrong, expired, used)    | P5     |
| presents a refused enrollment code only once (wrong, expired, used)                        | P5     |
| waits for Retry-After when rate-limited; pairs once the limit lifts                        | P6     |

The core’s own rules (C1 to C6, the race of P4, I3, U4, the limits) are proven by its tests:
[`tests/modules/satellites/`](https://github.com/nestor-home/nestor/tree/main/tests/modules/satellites),
[`test_gateway.py`](https://github.com/nestor-home/nestor/blob/main/tests/adapters/channels/satellites/test_gateway.py).
