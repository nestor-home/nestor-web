Nestor a besoin d’un **modèle de langage** pour l’agent, et de services de **parole** seulement
pour le canal vocal. On le joint par des **canaux** : Telegram, le canal vocal, ou les deux. Tout se
règle dans `nestor.yaml`, avec les clés dans le `.env` posé à côté. `nestor init` écrit OpenRouter
et ElevenLabs : choisissez un autre fournisseur ci-dessous, collez ses blocs à la place des blocs
correspondants, puis lancez `nestor check`.

## Modèle de langage

L’agent parle à tout serveur qui expose l’API Chat Completions d’OpenAI, en streaming.
L’adaptateur est testé avec OpenRouter ; les autres parlent la même API et devraient fonctionner.
Choisissez un modèle qui gère les appels d’outils : c’est par eux que l’agent agit.

Les noms de modèles sont des exemples : tout modèle du catalogue du fournisseur qui gère les appels
d’outils convient, et tout autre hébergeur compatible OpenAI se règle de la même façon. Sur la
plupart des machines domestiques, un modèle local répond plus lentement qu’un modèle hébergé, et
c’est le canal vocal qui le ressent en premier. Avec Docker, `localhost` désigne le conteneur
lui-même : utilisez `http://host.docker.internal:<port>` à la place.

`model` accepte aussi `extra_body`, fusionné dans chaque requête (routage d’OpenRouter, réglages de
raisonnement…), `connect_timeout_s` (5) et `read_timeout_s` (30). Un `triage_model` avec les mêmes
clés confie le tri des éléments entrants à un modèle plus petit.

## Parole

Le canal vocal transcrit la personne et dit la réponse. ElevenLabs est aujourd’hui le seul
fournisseur, pour les deux ; un autre ne sera ajouté qu’après avoir tenu sur des mesures reproductibles
(latence, fins de tour, interruptions).

<Providers kind="speech" locale="fr">
<ProviderSetup kind="speech" brand="elevenlabs">

Scribe v2 Realtime transcrit, v4 Turbo parle ; une seule clé couvre les deux.

```bash
ELEVENLABS_API_KEY=sk_...
```

```yaml
channels:
  - kind: voice
    room: salon
    host: 0.0.0.0
    speech:
      api_key: ${ELEVENLABS_API_KEY}
      voice_id: GPAQQPp9dazaB2bl4zg9
```

`voice_id` est n’importe quelle voix de votre bibliothèque ElevenLabs. La voix suit la langue du
texte ; la transcription attend de l’anglais, sauf si `speech` fixe une autre `language` (voir plus
bas).

</ProviderSetup>
</Providers>

## Canaux

Chaque canal est une entrée de `channels`, et plusieurs peuvent tourner ensemble, avec la même
mémoire. Telegram est livré avec le paquet. Le canal vocal est l’extra `voice` (voir
[Installer](/fr/docs/install/)) : la voix en temps réel dans un navigateur et sur les
[satellites](/fr/docs/satellites/), avec les services de parole ci-dessus.

<Providers kind="channel" locale="fr">
<ProviderSetup kind="channel" brand="telegram">

Créez un bot avec [@BotFather](https://t.me/BotFather) sur Telegram et mettez son jeton dans
`.env` :

```bash
TELEGRAM_BOT_TOKEN=123456:ABC-...
```

```yaml
channels:
  - kind: telegram
    token: ${TELEGRAM_BOT_TOKEN}
```

Ajoutez `"telegram:<votre chat id>"` à vos `accounts` dans `household` pour que le bot vous
reconnaisse. Il lit les messages texte ; les messages vocaux et les photos sont ignorés.

</ProviderSetup>
<ProviderSetup kind="channel" brand="voice">

Installez l’extra `voice` (l’image Docker le contient), puis ajoutez le canal avec son fournisseur
de parole :

```yaml
channels:
  - kind: voice
    room: salon
    host: 0.0.0.0
    speech:
      api_key: ${ELEVENLABS_API_KEY}
      voice_id: GPAQQPp9dazaB2bl4zg9
```

`room` est la pièce où se tient la conversation vocale. `host: 0.0.0.0` permet aux satellites de
votre réseau de joindre le serveur ; appairez-les ensuite comme l’explique
[Satellites](/fr/docs/satellites/).

</ProviderSetup>
</Providers>

## En français

Nestor parle anglais par défaut. Pour un foyer francophone, réglez la langue de la persona et, avec
le canal vocal, celle de la transcription :

```yaml
persona:
  language: French

channels:
  - kind: voice
    speech:
      language: fr
```

## Où ranger les clés

- **`.env`**, à côté de `nestor.yaml`, appelé par `${NOM}` : ce qu’écrit `nestor init` et ce
  qu’utilisent les blocs ci-dessus. Une variable déjà définie dans l’environnement (le shell, un
  gestionnaire de services, Docker) l’emporte sur le fichier.
- **Le coffre**, chiffré dans le dossier de données, appelé par `${secret:nom}` : réglé avec
  `nestor secrets set <nom>` (saisi sans écho) ou depuis l’administration, listé avec
  `nestor secrets list`. Mieux vaut y passer une fois l’installation stabilisée : aucune clé ne
  reste en clair sur le disque, et l’administration peut les changer.

```bash
nestor secrets set openrouter   # puis, dans nestor.yaml : api_key: ${secret:openrouter}
```

`NESTOR_SECRET_KEY`, dans `.env`, ouvre le coffre. `nestor init` le génère : ne le changez jamais,
sinon les secrets déjà rangés deviennent illisibles. Redémarrez Nestor après avoir changé une clé.
