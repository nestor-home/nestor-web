L’agent pense avec un modèle de langage que vous choisissez. Nestor parle à tout serveur qui expose
l’API Chat Completions d’OpenAI, en streaming : un fournisseur hébergé, ou un serveur sur votre
propre machine. Choisissez un modèle qui gère les appels d’outils : c’est par eux que l’agent agit.

## Choisir un fournisseur

Chaque modèle est un profil sous `models`, avec un nom que vous choisissez. `nestor init` en écrit
un, `main`. Pour changer de fournisseur, remplacez son bloc par l’un de ceux ci-dessous, puis lancez
`nestor check`.

La clé va dans `.env`, en `MODEL_API_KEY`, quel que soit le fournisseur. Les serveurs locaux n’en
demandent pas : laissez-la vide. L’adaptateur est testé avec OpenRouter ; les autres parlent la même
API et devraient fonctionner.

Les noms de modèles sont des exemples : tout modèle du catalogue du fournisseur qui gère les appels
d’outils convient, et tout autre hébergeur compatible OpenAI se règle de la même façon. Sur la
plupart des machines domestiques, un modèle local répond plus lentement qu’un modèle hébergé, et
c’est la voix qui le ressent en premier.

Avec Docker, `localhost` désigne le conteneur lui-même. Un serveur de modèle qui tourne sur l’hôte
est à l’adresse `http://host.docker.internal:<port>/v1` : `http://host.docker.internal:11434/v1`
pour Ollama, `http://host.docker.internal:1234/v1` pour LM Studio. Sous Linux, cette adresse n’est
pas la boucle locale de l’hôte : le serveur de modèle doit donc écouter au-delà
(`OLLAMA_HOST=0.0.0.0` pour Ollama, `--host 0.0.0.0` pour llama.cpp).

## Rôles

Avec un seul modèle, il fait tout. Avec plusieurs, chaque rôle dit lequel utiliser, par son nom dans
`models` :

| Rôle                   | Ce qu’il fait                                                   | Sans réglage           |
| ---------------------- | --------------------------------------------------------------- | ---------------------- |
| `agent.spoken`         | répond à voix haute : les premiers mots doivent venir vite       | `agent.written`        |
| `agent.written`        | répond par écrit, où quelques secondes ne gênent pas             | `agent.spoken`         |
| `agent.background`     | travaille sur un réveil qu’il a programmé, sans personne qui attend | `agent.written`     |
| `watches.model`        | trie le courrier entrant pour les veilles                        | `agent.written`        |
| `memory.consolidation` | résume chaque conversation une fois terminée                     | `agent.background`     |

Par exemple, un modèle rapide pour la voix et un plus solide pour tout le reste :

```yaml
models:
  quick:
    kind: openai-compatible
    base_url: https://openrouter.ai/api/v1
    api_key: ${MODEL_API_KEY}
    model: anthropic/claude-haiku-5.5
  deep:
    kind: openai-compatible
    base_url: https://openrouter.ai/api/v1
    api_key: ${MODEL_API_KEY}
    model: anthropic/claude-sonnet-5.5

agent:
  spoken: quick
  written: deep
```

Les profils peuvent viser des fournisseurs différents, chacun avec sa clé dans `.env`.

## Recherche par le sens

Nestor retrouve souvenirs et conversations passées par leurs mots. Avec un modèle d’embedding, il
les retrouve aussi par le sens : « que mange Léa ? » trouve alors « Léa est végétarienne ». Ajoutez
un profil d’embedding et nommez-le dans `memory.embedder` :

```yaml
models:
  vectors:
    kind: openai-compatible-embeddings
    base_url: https://openrouter.ai/api/v1
    api_key: ${MODEL_API_KEY}
    model: openai/text-embedding-3-small
    dimensions: 1536

memory:
  embedder: vectors
```

Tout serveur qui expose un point `/embeddings` compatible OpenAI convient, `llama-server
--embeddings` de llama.cpp compris. `dimensions` est la taille des vecteurs qu’il renvoie.
`query_prefix` et `document_prefix` ajoutent le texte que certains modèles attendent devant une
question ou un document. Changer de modèle plus tard réindexe tout, en tâche de fond.
[Mémoire](/fr/docs/agent/memory/) montre comment les deux recherches se combinent.

## Réglages

Un profil de conversation accepte aussi :

- `extra_body`, fusionné dans chaque requête : routage d’OpenRouter, réglages de raisonnement… ;
- `connect_timeout_s` (5) et `read_timeout_s` (30), en secondes ;
- `cache_control`, qui marque la partie stable des consignes pour le cache de prompt du
  fournisseur. Actif par défaut pour OpenRouter et Anthropic.
