Voici le standard que tout satellite implémente, en version 1 ([historique](#13-historique)). La
[suite de conformité](/fr/docs/satellites/conformance/) boîte noire du cœur y confronte les SDK et
les pilotes.

Un **satellite** est un appareil appairé à un serveur Nestor (le **cœur**). Il parle avec
l’assistant par écrit, à voix haute ou les deux, remonte des observations et exécute les intentions
du cœur.

DOIT, NE DOIT PAS, DEVRAIT, NE DEVRAIT PAS et PEUT s’entendent au sens de la
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) (MUST, MUST NOT, SHOULD, SHOULD NOT, MAY). Les
classes de messages du cœur (`nestor.modules.satellites.wire`) font foi pour chaque message ; leurs
schémas JSON sont servis à `https://nestorhome.dev/schemas/satellite/1/<message>.json`
([Schémas](/fr/docs/satellites/schemas/)).

## 1. Vue d’ensemble

Un satellite passe par trois phases, dans cet ordre :

1. **L’appairage**, une fois : une personne prouve qu’elle voulait appairer l’appareil
   ([section 2](#2-méthodes-dappairage)), et le cœur lui remet un jeton ([section 3](#3-appairage)).
2. **Le lien**, tant que l’appareil tourne : un WebSocket ouvert avec le jeton, qui porte tous les
   messages ([section 7](#7-lien)).
3. **L’audio**, seulement pour un appareil autorisé : une connexion WebRTC liée au lien, qui ne
   porte que l’audio ([section 9](#9-audio)).

## 2. Méthodes d’appairage

L’appareil déclare les méthodes qu’il prend en charge et la personne en choisit une. Un **code
d’appareil** va de l’appareil à la personne, qui le tape dans l’administration. Un **code
d’enrôlement** va de l’administration à l’appareil, qui le présente au cœur.

| Méthode                   | Preuve            | La personne…                                                                                          |
| ------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------- |
| `device_code.display`     | code d’appareil   | lit le code sur l’écran de l’appareil et le tape dans l’administration                                |
| `device_code.speech`      | code d’appareil   | entend l’appareil dire son code et le tape dans l’administration                                      |
| `enrollment.input`        | code d’enrôlement | tape le code d’enrôlement sur l’appareil                                                              |
| `enrollment.provisioning` | code d’enrôlement | met l’URI ou le code d’appairage dans la configuration de l’appareil (option, environnement, fichier) |
| `enrollment.qr`           | code d’enrôlement | montre le QR code de l’URI d’appairage à la caméra de l’appareil                                      |

L’identification ([section 6](#6-identification)) est une capacité, pas une méthode.

### 2.1 Négociation

- **N1.** Un manifeste DOIT lister dans `pairing_methods` les méthodes que l’appareil prend en
  charge, au moins une, sans répétition. Un appareil NE DOIT PAS déclarer une méthode qu’il ne sait
  pas mener à bien.
- **N2.** Le cœur recommande la première méthode que l’appareil prend en charge dans cet ordre :
  `device_code.display`, `device_code.speech`, `enrollment.qr`, `enrollment.input`,
  `enrollment.provisioning`. Pour un appareil qui n’a pas encore contacté le cœur, toutes les
  méthodes sont proposées. L’administration met en avant la recommandée et garde les autres
  disponibles.
- **N3.** L’appareil n’impose jamais de méthode. Quoi que la personne choisisse, l’appareil DOIT
  accepter les deux preuves jusqu’à ce que l’une soit acceptée (section 3.3).

## 3. Appairage

### 3.1 Points d’accès

Tous les corps sont en JSON (`Content-Type: application/json`).

| Requête                                             | Corps                | Réponse                |
| --------------------------------------------------- | -------------------- | ---------------------- |
| `POST /satellites/pairings`                         | `pairing.request`    | `201` `pairing.ticket` |
| `POST /satellites/pairings/{pairing_id}/enrollment` | `pairing.enrollment` | `200` `pairing.state`  |
| `GET /satellites/pairings/{pairing_id}`             |                      | `200` `pairing.state`  |

```json
POST /satellites/pairings
{"manifest": {"protocol": "nestor.satellite/1",
              "device": {"id": "capteur-entree", "model": "esp32", "room": "entree"},
              "software": {"name": "nestor-satellite", "version": "0.5.0"},
              "capabilities": [{"name": "device.identify"}],
              "pairing_methods": ["enrollment.provisioning", "enrollment.qr"]},
 "enrollment_code": "K7QF2M9X", "method": "enrollment.provisioning"}

201 {"pairing_id": "…", "status": "approved", "expires_at": "2026-10-30T12:10:00+00:00"}
201 {"pairing_id": "…", "status": "pending", "expires_at": "…", "device_code": "042917"}   (sans code)

GET /satellites/pairings/{pairing_id}
200 {"status": "pending", "identify": true}
200 {"status": "approved", "token": "nst1_…", "device_id": "capteur-entree", "room": "entree",
     "capabilities": ["device.identify"]}
```

Une erreur renvoie un `pairing.error` : `{"error": code, "detail": texte, "reason"?: …,
"retry_after_s"?: …}`.

| `error`                | Statut | Sens                                                                                            |
| ---------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| `invalid_request`      | 422    | le corps ne suit pas son schéma                                                                 |
| `protocol_unsupported` | 422    | le manifeste nomme une autre version de ce protocole                                            |
| `too_many_pending`     | 429    | trop d’appareils attendent une preuve ; `Retry-After` et `retry_after_s` disent quand réessayer |
| `too_many_attempts`    | 429    | trop de codes d’enrôlement faux ; `Retry-After` et `retry_after_s` disent quand réessayer       |
| `enrollment_refused`   | 403    | le code d’enrôlement n’appaire rien ; `reason` vaut `unknown`, `expired`, `used` ou `cancelled` |
| `not_pending`          | 409    | l’appairage n’attend plus de preuve : l’autre preuve l’a emporté, ou il a expiré                |

`detail` est en anglais, pour les journaux. Un appareil qui affiche ou énonce une erreur DOIT la
traduire à partir de `error` et `reason`, jamais afficher `detail`.

### 3.2 États d’un appairage

<PairingStates locale="fr" n={2} />

- Un appairage en attente dure 10 minutes. Un `pairing_id` inconnu, remplacé ou oublié se lit
  `expired` : interroger ne révèle rien.
- Seule la première réponse `approved` porte le jeton ; les lectures suivantes donnent `claimed`.

### 3.3 Règles de l’appareil

- **P1.** Un appareil DOIT prendre en charge `enrollment.provisioning` : il lit une URI d’appairage
  dans `NESTOR_PAIRING_URI`, ou un code d’enrôlement dans `NESTOR_PAIRING_CODE` avec l’adresse du
  cœur donnée à part. Il DEVRAIT aussi accepter les deux par une option de ligne de commande et dans
  son fichier de configuration.
- **P2.** Sans code d’enrôlement, un appareil DOIT demander un appairage et présenter son code
  d’appareil sur toutes ses sorties : à l’écran (`device_code.display`), à voix haute, et toujours
  dans son journal. À voix haute (`device_code.speech`), c’est une courte phrase, puis les chiffres
  un par un avec une pause entre chacun, le tout dit deux fois, dans la langue de l’appareil, sans
  réseau. Un appareil sans écran ni voix DOIT écrire dans son journal le code d’appareil et qu’un
  code d’enrôlement l’appaire. L’appareil interroge environ une fois par seconde jusqu’à ce que
  l’appairage soit approuvé ou expire, et redemande s’il expire.
- **P3.** Un appareil qui a un code d’enrôlement DOIT l’envoyer dans sa requête, avec la méthode par
  laquelle il l’a reçu. Il NE DOIT PAS présenter de code d’appareil, sauf si ce code est refusé.
- **P4.** Un appareil en attente DOIT accepter un code d’enrôlement à tout moment (tapé, scanné,
  configuré) et l’envoyer à `POST …/{pairing_id}/enrollment`. La première preuve acceptée
  l’emporte :
  - si le code d’appareil a été tapé d’abord, l’enrôlement répond `not_pending` et le code
    d’enrôlement n’est **pas** consommé : l’appareil continue d’interroger et obtient son jeton ;
  - si le code d’enrôlement a été accepté d’abord, le code d’appareil tapé ensuite est refusé.
    Sur `approved`, l’appareil cesse aussitôt de présenter son code d’appareil (une voix se tait).
- **P5.** Un code d’enrôlement refusé par `enrollment_refused` NE DOIT PLUS être présenté, même
  après un redémarrage : l’appareil garde les codes refusés avec son jeton (une empreinte de chacun
  suffit). Il DOIT le dire dans son journal (et sur ses sorties, traduit), puis se rabattre sur un
  code d’appareil (P2).
- **P6.** Sur un `429`, un appareil DOIT attendre au moins `Retry-After` secondes avant de
  réessayer.
- **P7.** Les codes d’enrôlement DOIVENT être normalisés avant envoi (section 4.2). Un appareil
  PEUT les envoyer tels que tapés : le cœur normalise aussi.
- **P8.** Un appareil DOIT garder son jeton secret (lisible par son seul propriétaire sur un système
  de fichiers), l’oublier quand le cœur le refuse (lien fermé avec `4401`, ou `401` sur une offre
  audio), puis s’appairer à nouveau.

### 3.4 Règles du cœur

- **C1.** Le cœur accepte les versions du protocole qu’il parle : `nestor.satellite/1`. Un
  manifeste qui nomme un autre `nestor.satellite/<n>` est refusé avec `protocol_unsupported`. Un
  cœur PEUT accepter aussi la version précédant la sienne, pour que les appareils se mettent à jour
  après lui.
- **C2.** Un code d’enrôlement appaire un seul appareil. Il est consommé dès qu’il est accepté,
  avant que quoi que ce soit puisse l’observer : de deux appareils qui l’utilisent en même temps,
  l’un est approuvé, l’autre reçoit `enrollment_refused` (`used`).
- **C3.** Une preuve n’est acceptée que tant que son appairage est `pending` ; la première acceptée
  le fait passer aussitôt à `approved`. Un code d’enrôlement refusé parce que l’appairage n’est plus
  en attente n’est pas consommé.
- **C4.** Le jeton compte 256 bits aléatoires, précédés de `nst1_` ; seul son SHA-256 est conservé.
- **C5.** Une nouvelle demande avec le même identifiant d’appareil remplace la demande en attente.
- **C6.** Le journal enregistre chaque étape : `satellite.pairing.requested` (avec les méthodes
  déclarées), `satellite.addition.started|completed|cancelled|expired`,
  `satellite.enrollment.refused` (avec sa raison et l’adresse), `satellite.paired` (avec la preuve,
  la méthode et l’ajout), `satellite.identify.requested`, `satellite.revoked`, puis
  `satellite.connected` (avec le logiciel et le protocole de chaque `hello`) et les mises à jour
  (section 10). Jamais un code ni un jeton en clair.

### 3.5 Ajouts

Un **ajout** est la façon dont une personne ajoute un satellite depuis l’administration : une
méthode et, si elle le veut, un nom, une pièce et le plafond des capacités à autoriser. Il dure
15 minutes par défaut (de 1 minute à 7 jours).

- Avec une méthode d’enrôlement, l’ajout crée le code d’enrôlement, rendu une seule fois avec son
  URI d’appairage. L’appareil qui le présente est appairé aussitôt, sous le nom et dans la pièce de
  l’ajout, ses capacités déclarées restreintes à celles de l’ajout.
- Avec une méthode par code d’appareil, l’administration liste les appareils en attente. La
  personne les distingue (identification) et tape le code du bon ; le nom, la pièce et les
  capacités de l’ajout s’appliquent.

Un ajout se termine quand son appareil est appairé (`completed`), quand il est annulé ou quand il
expire. Il y en a au plus 32 en cours. Le cœur réserve un ajout en une seule opération : si deux
personnes tapent un code pour lui au même instant, un seul appareil s’appaire et l’autre personne
apprend que l’ajout est terminé.

## 4. Codes et URI

### 4.1 Code d’appareil

Six chiffres décimaux aléatoires (`042917`), uniques parmi les appairages en attente.

### 4.2 Code d’enrôlement

- Huit symboles de l’alphabet base32 de Crockford `0123456789ABCDEFGHJKMNPQRSTVWXYZ` : 40 bits
  aléatoires.
- Affiché par groupes de quatre : `K7QF-2M9X`.
- Normalisation, avant toute comparaison : retirer espaces et tirets, passer en majuscules, puis
  remplacer `O` par `0`, `I` et `L` par `1`. Un résultat qui ne fait pas 8 symboles de l’alphabet
  n’est pas un code (`U` n’en est jamais un).
- Forme canonique : les 8 symboles normalisés, sans tiret.

### 4.3 URI d’appairage

```text
nestor+http://nestor.local:8471/?code=K7QF2M9X
nestor+https://nestor.example.org/satellites-proxy/?code=K7QF2M9X
```

- Le schéma est `nestor+` suivi du schéma de l’URL de base du cœur (`http` ou `https`). Retirer
  `nestor+` et la requête donne l’URL de base.
- `code` est le code d’enrôlement, sous forme canonique.
- L’administration renvoie l’URI ; une interface dessine son QR code elle-même.

## 5. Manifeste

```json
{
  "protocol": "nestor.satellite/1",
  "device": { "id": "salon", "model": "reachy-mini", "room": "salon", "brand": "pollen-robotics" },
  "software": { "name": "nestor-reachy", "version": "0.4.0" },
  "capabilities": [{ "name": "audio.capture" }, { "name": "audio.playback" }, { "name": "device.identify" }],
  "pairing_methods": ["device_code.speech", "enrollment.provisioning"]
}
```

`id` et `room` sont des identifiants en minuscules (`^[a-z0-9][a-z0-9_-]{0,63}$`). Les capacités
sont des noms `famille.fonction`, 32 au plus, chacune déclarée une fois. Le manifeste est envoyé à
l’appairage et dans `hello`.

`software` est obligatoire : le paquet que l’appareil fait tourner, nommé comme il est installé
(`nestor-reachy` depuis PyPI, `@nestor-home/satellite` depuis npm), et sa version, de 1 à
64 caractères chacun. L’administration l’affiche, et un appareil qui se met à jour lui-même
(section 10) installe les versions plus récentes de ce paquet.

| Capacité                  | L’appareil…                                         |
| ------------------------- | --------------------------------------------------- |
| `text.input`              | envoie ce qu’une personne a tapé (section 8)        |
| `text.display`            | affiche les mots de l’assistant (section 8)         |
| `audio.capture`           | envoie son micro (section 9)                        |
| `audio.playback`          | joue la voix du cœur (section 9)                    |
| `audio.speech_activity`   | signale quand quelqu’un commence ou cesse de parler |
| `vision.person_detection` | signale les personnes qu’il voit                    |
| `expression.emotion`      | montre les émotions de l’assistant                  |
| `motion.head`             | bouge avec la parole de l’assistant                 |
| `device.identify`         | se fait remarquer sur demande (section 6)           |
| `device.update`           | installe une version plus récente de son logiciel sur demande (section 10) |

Un appareil sans `text.*` ni `audio.*` est un capteur ou un corps : il ne fait que remonter des
observations et exécuter des intentions.

## 6. Identification

- **I1.** Un appareil qui déclare `device.identify` DOIT, sur une réponse d’attente portant
  `"identify": true`, se faire remarquer quelques secondes avec les sorties dont il dispose
  (clignoter, remuer, sonner, faire scintiller son écran), et continuer d’interroger.
- **I2.** Une fois appairé et autorisé à `device.identify`, il DOIT accuser réception de
  `intent.identify` comme de toute intention, et se faire remarquer de la même façon.
- **I3.** Le cœur n’envoie l’identification qu’à un appareil qui l’a déclarée (en attente) ou qui y
  est autorisé (appairé). L’administration la refuse sinon, ainsi que pour un appareil appairé qui
  n’est pas connecté.
- L’identification aide seulement une personne à distinguer des appareils. Elle ne prouve rien et
  ne remplace jamais un code.

## 7. Lien

- **L1.** Avec son jeton, l’appareil ouvre un WebSocket sur `/satellites/{device_id}/link`, sous
  l’URL de base du cœur (`ws://` pour `http`, `wss://` pour `https`). Son premier message DOIT être
  `hello` : son manifeste, avec l’identifiant appairé, et son jeton. Le cœur répond `welcome` : la
  pièce appairée et les capacités autorisées.
- **L2.** Le cœur ferme le lien sans `welcome` quand `hello` tarde (10 s), sort du contrat ou vise un
  autre appareil (`4400`), ou quand le jeton est refusé (`4401`). Sur `4401`, l’appareil DOIT
  oublier son jeton et s’appairer à nouveau (P8).
- **L3.** Chaque message est `{"type", "id", "at", "payload"}`, un par trame texte du WebSocket.
  L’appareil DOIT accuser réception de chaque `intent.*` avec `ack` en moins d’une seconde, et NE
  DOIT envoyer que ce qu’on lui a autorisé : observations, `input.text` (section 8), `update.status`
  (section 10). Les types de message inconnus venant du cœur sont ignorés.
- **L4.** Un appareil tient un seul lien. Un nouveau lien du même appareil remplace le précédent, que
  le cœur ferme avec `4409`. Le cœur envoie un ping toutes les 20 s (pings WebSocket). Un appareil qui
  les voit DEVRAIT tenir le lien pour perdu après 60 s sans aucun ; celui qui ne les voit pas (le
  WebSocket d’un navigateur les cache) compte sur le transport pour fermer le lien.
- **L5.** Quand le cœur ferme le lien (`1001` à son arrêt) ou que le lien est perdu, l’appareil se
  reconnecte avec le même jeton, en espaçant ses tentatives.

| Code de fermeture | Sens                                                      | L’appareil…                          |
| ----------------- | --------------------------------------------------------- | ------------------------------------ |
| `1001`            | le cœur s’arrête                                          | se reconnecte (L5)                   |
| `4400`            | `hello` en retard, hors contrat ou pour un autre appareil | se corrige, puis se reconnecte       |
| `4401`            | le jeton est refusé                                       | l’oublie et s’appaire à nouveau (P8) |
| `4409`            | un lien plus récent de cet appareil a remplacé celui-ci   | s’arrête : l’autre lien fait foi     |

## 8. Texte

- **T1.** Un appareil autorisé à `text.input` envoie ce qu’une personne a tapé en `input.text`.
  Chacun est un tour de la conversation de la pièce de l’appareil.
- **T2.** Un appareil autorisé à `text.display` reçoit les mots de l’assistant en `intent.text`, dans
  l’ordre, et les affiche. Une réponse peut tenir en plusieurs messages (un point d’étape, puis le
  résultat) ; `final` marque le dernier d’un tour. Un message spontané (un rappel, une annonce) est
  un seul `intent.text`, `final` posé.
- **T3.** Un tour tapé reçoit une réponse écrite quand l’appareil est autorisé à `text.display`,
  sinon à voix haute. Un tour parlé reçoit une réponse à voix haute ; un appareil aussi autorisé à
  `text.display` affiche les mêmes mots à mesure qu’ils sont dits.
- **T4.** `input.text` tient 1 à 4 000 caractères, `intent.text` jusqu’à 16 000. Le texte est brut,
  sans Markdown.

## 9. Audio

- **A1.** Un appareil autorisé à `audio.capture` ou `audio.playback` (dans `welcome`) propose une
  connexion WebRTC une fois accueilli : `POST /satellites/{device_id}/audio` avec
  `Authorization: Bearer <jeton>` et `{"sdp", "type"}` ; le cœur répond `{"sdp", "type", "pc_id"}`.
  Les candidats ICE suivent en `PATCH` sur le même chemin. Un mauvais jeton reçoit `401` ; un
  appareil sans lien ou non autorisé à l’audio, `403` ; le `pc_id` d’un autre appareil, `403`.
- **A2.** La connexion ne porte que de l’audio Opus : la voix du cœur vers l’appareil
  (`audio.playback`), le micro vers le cœur (`audio.capture`). Les messages ne passent jamais par
  WebRTC.
- **A3.** L’audio vit avec le lien : quand le lien se ferme, le cœur raccroche l’audio. Tant que le
  lien tient, un appareil dont l’audio tombe propose à nouveau, en espaçant ses tentatives.
- **A4.** Un appareil n’ouvre son micro que pour cette connexion. Ni l’appairage ni le lien ne
  l’attendent, car un navigateur peut attendre qu’une personne autorise le micro.

## 10. Mises à jour

Un appareil autorisé à `device.update` installe une version plus récente de son propre logiciel
quand une personne le demande depuis l’administration. Le cœur ne nomme jamais une source ni un
fichier : il transmet seulement la version que l’appareil a trouvée lui-même. Un cœur compromis peut
au plus demander à un appareil une version à laquelle il fait déjà confiance.

```json
{"type": "update.status", "id": "…", "at": "…", "payload": {"state": "available", "version": "0.5.1", "notes": "https://github.com/…/releases/tag/v0.5.1"}}
{"type": "intent.update", "id": "…", "at": "…", "payload": {"version": "0.5.1"}}
```

| `state`      | Sens                                                                                    | `version`     |
| ------------ | --------------------------------------------------------------------------------------- | ------------- |
| `current`    | il n’a rien trouvé de plus récent                                                       | absente       |
| `available`  | une version plus récente peut être installée                                            | cette version |
| `installing` | il installe cette version, puis redémarre dessus                                        | cette version |
| `failed`     | la version ne s’est pas installée ou n’a pas démarré : il est revenu à celle qu’il avait | cette version |

- **U1.** Un appareil ne déclare `device.update` que s’il sait installer son logiciel lui-même. Une
  fois accueilli et autorisé, il cherche une version plus récente de `software.name` à sa propre
  source (l’index d’où il a été installé, jamais une adresse donnée par le cœur), et envoie
  `update.status` au début de chaque lien. Il cherche à nouveau au plus une fois par jour.
- **U2.** Il accuse réception de `intent.update` comme de toute intention, et n’installe que la
  version plus récente qu’il a trouvée et signalée. Une version plus ancienne, ou qu’il n’a jamais
  signalée, est acquittée et pas installée.
- **U3.** Il signale `installing`, installe la version, puis redémarre dessus. La nouvelle version
  DOIT être accueillie en moins de 60 s ; sinon l’appareil revient à la version qu’il avait et
  signale `failed` avec la version essayée. Une installation qui échoue signale `failed` aussi.
- **U4.** Le cœur n’envoie `intent.update` que quand une personne le demande dans l’administration,
  qu’à un appareil connecté autorisé à `device.update`, et qu’avec la version que cet appareil a
  signalée comme `available`. Le journal garde `satellite.update.requested` et chaque état signalé
  par l’appareil (`satellite.update.reported`) ; la nouvelle version apparaît dans le
  `satellite.connected` suivant.
- **U5.** Avec tout état sauf `current`, un appareil PEUT ajouter `notes` : une adresse https (512
  caractères au plus) de ce que change cette version, trouvée à la même source. L’administration
  l’affiche comme un lien que le navigateur de la personne ouvre ; le cœur ne la consulte jamais.

## 11. Sécurité

- **Entropie.** Un code d’enrôlement a 40 bits. Avec au plus 32 codes en cours et 5 codes faux par
  minute et par adresse (20 toutes adresses confondues), les 300 essais d’une durée de vie de
  15 minutes trouvent un code environ une fois sur 10⁸. Un code d’appareil a 20 bits, mais seule
  une personne connectée le tape, sur un appairage en attente qu’elle a choisi, dans les 10 minutes.
- **Durée de vie.** Les codes d’enrôlement durent 15 minutes par défaut, 7 jours au plus ; les codes
  d’appareil, 10 minutes. Un code d’enrôlement accepté est consommé aussitôt (C2).
- **Limites de débit.** Les codes d’enrôlement faux sont comptés par adresse cliente et au total sur
  une minute glissante. Au-delà de l’une ou l’autre limite, chaque tentative, juste ou fausse,
  reçoit `429` jusqu’à ce que la fenêtre libère une place : un client limité n’apprend rien.
- **Empreintes.** Seuls les SHA-256 des codes et des jetons sont stockés et journalisés, et comparés
  en temps constant. L’empreinte divulguée d’un code de 40 bits se casse hors ligne : gardez des
  durées de vie courtes.
- **Transport.** Codes et jetons traversent le réseau en clair sur `http` et `ws` ; utilisez
  `https` (une URI `nestor+https`, donc `wss`) hors d’un réseau domestique de confiance. Le cœur ne
  journalise jamais le jeton de `hello`.
- **L’identification** montre quel appareil répond, pas que c’est celui que la personne a en main :
  n’appairez jamais sur la seule identification.
- **Consentement.** Un appareil ne reçoit que les capacités qu’une personne a autorisées, jamais
  plus que ce qu’il a déclaré.
- **Mises à jour.** Un appareil récupère une nouvelle version à sa propre source, avec les
  contrôles d’intégrité de celle-ci, et seulement la version qu’il a signalée (U1, U2). Un appareil
  qui ne sait pas se mettre à jour sans risque ne déclare pas `device.update`.

## 12. Conformité

La [suite de conformité](/fr/docs/satellites/conformance/) vérifie les règles de l’appareil :

| Vérification                                                                                    | Règles |
| ----------------------------------------------------------------------------------------------- | ------ |
| déclare enrollment.provisioning                                                                 | N1, P1 |
| demande à s’appairer ; réclame son jeton une fois son code d’appareil tapé                      | P2     |
| continue d’interroger après une identification en attente (s’il déclare `device.identify`)      | I1     |
| ouvre son lien avec son jeton ; envoie d’abord un hello ; se présente comme l’appareil appairé  | L1     |
| accuse réception de chaque intention en moins d’1 s (`intent.identify`, `intent.update` s’il y est autorisé) | L3, I2 |
| dit où en est son logiciel (s’il déclare `device.update`)                                       | U1     |
| n’installe jamais une version qu’il n’a pas signalée (s’il déclare `device.update`)             | U2     |
| chaque message suit son schéma                                                                  | L3     |
| oublie un jeton refusé et s’appaire à nouveau                                                   | L2, P8 |
| se reconnecte avec le même jeton quand le cœur ferme le lien                                    | L5     |
| accuse réception de `intent.text` (s’il déclare `text.display`)                                 | L3, T2 |
| reçoit l’audio du cœur ; envoie l’audio de son micro (s’il déclare `audio.*`)                   | A1, A2 |
| ne propose pas d’audio quand l’audio n’est pas autorisé                                         | A1     |
| s’appaire avec le code d’enrôlement de `NESTOR_PAIRING_URI`, sans code tapé                     | P3, P4 |
| se rabat sur un code d’appareil après le refus de son code d’enrôlement (faux, expiré, utilisé) | P5     |
| ne présente qu’une fois un code d’enrôlement refusé (faux, expiré, utilisé)                     | P5     |
| attend Retry-After quand il est limité ; s’appaire une fois la limite levée                     | P6     |

Les règles propres au cœur (C1 à C6, la course de P4, I3, U4, les limites) sont vérifiées par ses
tests :
[`tests/modules/satellites/`](https://github.com/nestor-home/nestor/tree/main/tests/modules/satellites),
[`test_gateway.py`](https://github.com/nestor-home/nestor/blob/main/tests/adapters/channels/satellites/test_gateway.py).
